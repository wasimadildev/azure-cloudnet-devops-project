01 Why firewall

Central policy
for network paths.

NSGs protect subnet or NIC boundaries. Azure Firewall provides centralized inspection, network rules, application rules, logging, and controlled next hops.

NSG

Local boundary

Subnet / NICpriority rules / stateful filtering

Answers: is this resource traffic allowed?

AZURE FIREWALL

Central control

Hub / transit pathpolicy / inspection / logs

Answers: should this network path be inspected and permitted?

↗

Firewall does not replace NSGs. A mature design uses both: local least privilege at the subnet and centralized policy across environments.

02 Firewall subnet

Give the firewall
its own home.

Azure Firewall requires a dedicated subnet named AzureFirewallSubnet. Reserve a sufficiently large range in the future hub VNet.

HUB VNETvnet-cloudnet-hub10.0.0.0/16
REQUIRED SUBNETAzureFirewallSubnet10.0.1.0/26Firewall only
TRANSITProduction / Dev10.10 + 10.20routed spokes
Dedicated boundary

Do not deploy VMs or unrelated resources in AzureFirewallSubnet. The exact sizing should follow your expected scale and Azure guidance.

04 Rule collections

Rules express
intent.

Firewall policy is organized into rule collections. Start with explicit network and application decisions; keep priorities deliberate.

Network rulesIP / port / protocol10.10.0.0/16 → 10.20.0.0/16 :443
Application rulesFQDN / HTTP / HTTPS*.github.com → HTTPS
DNAT rulesPublic → private destinationpublic:443 → internal:443
Rule principleDefault deny, explicit allow, documented source and destination.

Use Application Gateway for web edge routing and Firewall for centralized network/application policy. Keep their roles clear.

05 Build sequence

Create the
central control.

For this learning stage, create the hub firewall resources and inspect the policy model before adding broad routes.

  1. 01

    Create the hub VNet

    Use vnet-cloudnet-hub with 10.0.0.0/16. Keep it non-overlapping with production and development.

  2. 02

    Create AzureFirewallSubnet

    Add the required subnet name exactly: AzureFirewallSubnet. Reserve it for the firewall.

  3. 03

    Create Azure Firewall

    Use a Standard or Premium SKU according to the lab goal, attach a Standard static public IP, and place the firewall in the dedicated subnet.

  4. 04

    Create policy collections

    Start with narrow network/application rules. Do not add a default route to the firewall until the next-hop path is validated.

  5. 05

    Steer one test prefix

    Use a narrow UDR such as 10.20.0.0/16 → Virtual appliance → 10.0.1.4 before considering broader transit routes.

06 Firewall + NSG

Two controls,
one path.

Traffic can be routed through the firewall and still be blocked by the destination NSG. Both controls must agree.

WHERE?UDRsend destination prefix to firewall
INSPECT?Azure Firewallnetwork/application policy
ALLOWED?Destination NSGsubnet/NIC boundary
READY?Applicationlistener / service responds
!

Debug in order: effective route, firewall rule/log, NSG rule, then application health. A permit at one layer does not override a deny at another.

07 Safe routing

Never rush
the default route.

A 0.0.0.0/0 UDR catches almost all IPv4 traffic. Pointing it at an incomplete firewall path can break SSH, package updates, DNS, and NAT behavior.

Dangerous before validation0.0.0.0/0→ Virtual appliancecould blackhole broad traffic
Safer learning step10.20.0.0/16→ Virtual appliancenarrow test destination
Recovery mindset

Keep a tested management path. Apply one route change at a time, inspect effective routes, and remove a broken UDR before widening scope.
