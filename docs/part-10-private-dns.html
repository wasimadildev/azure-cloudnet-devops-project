01 Core concept

DNS answers
“where by name?”

The private endpoint provides the network interface. Private DNS provides the name-to-private-IP mapping that lets applications keep using normal Azure service hostnames.

Applicationstorage.blob.core.windows.net
Private DNS zoneprivatelink.blob.core.windows.net
A record10.10.3.x
Private Endpointpe-storage-cloudnet
↗

An endpoint can exist while DNS is wrong. If the hostname still resolves to a public address, the application may bypass the intended private path.

03 Zone design

private zone.

For Blob Storage, the documented private DNS zone is privatelink.blob.core.windows.net. The exact zone depends on the Azure service and subresource.

Do not use /etc/hosts

Hard-coded host entries do not scale across VMs, VNets, failover, or IaC. Use Azure Private DNS for the shared architecture.

04 Build sequence

Link the zone
to the network.

The Part 09 private endpoint may have created the zone automatically. This part makes the DNS objects explicit and prepares a second VNet link.

  1. 01

    Open Private DNS zones

    Open Private DNS zones and locate privatelink.blob.core.windows.net. Confirm the Storage A record exists.

  2. 02

    Inspect the VNet link

    Open Virtual network links and confirm vnet-cloudnet-prod is linked and enabled.

  3. 03

    Check the A record

    Open Record sets. The Storage Account record should point to the actual private endpoint IP, not an example address.

  4. 04

    Prepare development resolution

    After Part 09 peering is configured, link vnet-cloudnet-dev when development workloads need to resolve the same private service.

Azure CLI / private DNS
az network private-dns zone list \
  --resource-group rg-cloudnet-prod \
  --output table

az network private-dns link vnet list \
  --resource-group rg-cloudnet-prod \
  --zone-name privatelink.blob.core.windows.net \
  --output table

az network private-dns record-set a list \
  --resource-group rg-cloudnet-prod \
  --zone-name privatelink.blob.core.windows.net \
  --output table
Use the zone name created for your actual service. Do not assume every Azure service uses the Blob zone.

06 Production + dev

DNS scope follows
network scope.

After VNet peering, private DNS still needs deliberate design. Link the zone to every VNet that must resolve the private service, or centralize DNS in a hub design later.

PRODUCTIONvnet-cloudnet-prod10.10.0.0/16DNS link: yes
Private DNSlinked VNets
DEVELOPMENTvnet-cloudnet-dev10.20.0.0/16DNS link: add when needed
Peering is not DNS

VNet peering gives network reachability. A DNS zone link gives name resolution. You may need both.

07 Diagnosis

Debug name
resolution first.

When a private service call fails, follow the layers from hostname to authorization.

01Zone exists?az network private-dns zone list
02A record?record-set a list
03VNet linked?link vnet list
04Private answer?nslookup hostname
05TCP reachable?nc -vz IP 443
06Authorized?curl -I URL
!

Public DNS answer means stop. Fix the zone, record, VNet link, or VM DNS configuration before changing NSGs or application credentials.
