01 Hub-spoke model

Centralize what
should be shared.

The hub owns shared network services. Spokes own workloads. This separates platform governance from application lifecycle while preserving controlled private connectivity.

PRODUCTION SPOKEvnet-cloudnet-prod10.10.0.0/16web · API · data
peering
SHARED HUBvnet-cloudnet-hub10.0.0.0/16Firewall · Bastion · DNS
peering
DEVELOPMENT SPOKEvnet-cloudnet-dev10.20.0.0/16test workloads
↗

Spokes should not become a mesh by accident. Shared inspection and services live in the hub; routes define how spoke traffic reaches them.

05 Transit routing

Peering connects.
Routes control transit.

VNet peering provides private reachability, but centralized inspection requires UDRs that send spoke destinations to the firewall private IP.

Important limitation

Azure VNet peering is not automatically a transitive router. Design the hub route path and forwarded-traffic settings deliberately.

06 Build sequence

Assemble the
topology.

Build the hub foundation, peer each spoke, then add narrow transit routes before introducing broader enterprise policy.

  1. 01

    Confirm address spaces

    Hub 10.0.0.0/16, production 10.10.0.0/16, and development 10.20.0.0/16 must not overlap.

  2. 02

    Prepare shared subnets

    Reserve AzureFirewallSubnet, AzureBastionSubnet, and any shared gateway or DNS design before deployment.

  3. 03

    Create both peering directions

    Peer production↔hub and development↔hub. Enable the settings required for your firewall transit design.

  4. 04

    Apply narrow route tables

    Send one test destination, such as 10.20.0.0/16, to the firewall private IP before widening route scope.

  5. 05

    Verify effective routes

    Check the NIC route view, peering state, firewall logs, NSGs, and the application path together.
